# 輸出語言由使用者指定、預設英文，並由程式檢查

原本的語言規則是「用來源文件的語言」，由模型自行判斷。以 qwen3.8-flash-next 對英文的 cpe-inventory 案例跑 eval 時，6 次執行中有 3 次輸出中文：一次整份 Brief 都是中文，兩次是 Analysis 產生的矛盾、假設與問題理由是中文。trace 顯示模型的推理明確寫著 `Now write everything in English (documents are in English)` 與 `quotes are English… So write in English`，交出來的卻是中文。模型理解了規則也做出了正確判斷，生成時仍然漂移；在 prompt 補充語言規則後，情況沒有改善。因此語言不能只靠 prompt。

## 決定

- 輸出語言由使用者決定：config `outputLanguage` 或 CLI `--lang`（CLI 優先），值為 `en`（預設）、`zh`（繁體中文）、`cn`（簡體中文）。不再依來源文件判斷：Brief 是給團隊的產出，語言應該是團隊的選擇，而且「來源語言」在中英混合的文件上本來就沒有明確答案。
- prompt 明確寫出目標語言，並說明範例只示範結構。
- 交卷時由程式檢查每個條目中除了 Evidence、id、glossary `term` / `aliases` 以外的欄位：
  - `en`：不得出現中日文字。英文輸出裡的中文字必定是漂移，沒有灰色地帶。
  - `zh` / `cn`：不得出現另一種字體的專用字（157 組繁簡對照，只收只屬於一種字體的字，例如 这/這；兩種字體共用的字如 后、里、面、准不列入），而且長段敘述欄位（8 個英文單字以上且沒有中文字）不得是英文。
- 語言錯誤與 Evidence 錯誤一樣回饋重交；但最後一次仍不符合時**保留條目並寫入警告**，不當成 Rejected Item。內容本身是正確的，剔除只會損失資訊，還可能讓整次執行觸發 30% 的排除門檻。

## Consequences

- 每次漂移要多一次完整重交，以 cpe-inventory 為例約 2.5～3 萬輸出 tokens、1～2 分鐘。
- 繁簡檢查是清單法，涵蓋高頻字：真正漂到另一種字體時整段都會換，「这、为、个、们」等字幾乎必然出現；零星一兩個不在清單內的字（例如 鉴、赏）會漏掉。
- 識別名稱保留原文、名稱則要翻譯：中文文件以 `en` 輸出時，Actor「會員」會寫成 Member，glossary 的 term 仍是「鑑賞期」。
- eval 案例以 `language` 指定輸出語言，因為關鍵字標註必須與輸出同語言；既有的中文案例設為 `zh`。
